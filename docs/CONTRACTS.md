# A.R.M.O.R. contracts

The JSON Schemas in `src/armor_common/schemas/` are the **single source of truth**
for every message. Nothing else may add a rule the schema does not state, and
nothing may ignore one.

## Broker namespace

The nodes that read solar inverters and batteries publish on their own topic family, `armor/solar/{node_id}/{device}/state`, with the message's own
`kind` (`inverter` or `battery`) inside the payload (see *Solar messages* below). The nodes that measure the house's electrical network publish `armor/electrical/{node_id}/state` (see *Electrical messages*); a node that has switches also reads `armor/electrical/{node_id}/command` and answers on `armor/electrical/{node_id}/result` (see *Switches*). The radar family is
`armor/node/{node_id}/{kind}` where `kind` is `telemetry`, `health`, `info` or `command`.
Topic names are lower-case and part of the compatibility contract. A producer
keeps its `node_id` identical in the topic and in the JSON body; consumers reject
a mismatch.

| Kind | Direction | Schema |
|---|---|---|
| `telemetry` | node → server | `telemetry.schema.json`: node id, millisecond timestamp, ambient lux (0–200 000) and at most 15 tracks (5 per each of the 3 radar sensors). The limit stops an unbounded payload from exhausting a field node. |
| `health` | node → server | `health.schema.json`: node id, timestamp, `online` flag and, optionally, `kind` (`radar`, the default, or `panel` for a wall panel, which the server keeps apart from the radars) |
| `info` | node → server | `info.schema.json`: node id, timestamp, the operator's name for the node, its firmware version, its IPv4 address and the port of its web panel. It lets a console offer a link to the panel; it is sent when the node connects and now and then. |
| `command` | server → node | `command.schema.json`: `calibrate`, `set_thresholds` (optional `sensitivity` 1–10) or `restart`. Commands are an allow-list: a subscriber rejects everything else before it reaches hardware control logic. **Reserved:** nothing publishes this topic and no node listens to it today; the contract is kept so that a command channel to the radar nodes can use it later. |

All four use `additionalProperties: false`: an unknown field is an error, never
silently ignored.

## Node health (every family)

`armor/health/{node_id}` (node → server, `node_health.schema.json`, reports never retained), one message about once a minute from a node of **any** family. It is not the presence message of a radar (`armor/node/{node_id}/health`, above): that one says only whether the node is there; this one says how it is doing, in the same words for the five families.

* **Required:** `kind` (`node_health`), `node_id`, `timestamp_ms`, `family` (`radar`, `solar`, `electrical`, `alarm`, `hmi`), `firmware` (three parts, or four from 0.8.0), `uptime_s`, `reset_reason` (`power_on`, `external`, `software`, `panic`, `int_wdt`, `task_wdt`, `other_wdt`, `deep_sleep`, `brownout`, `sdio`, `usb`, `jtag`, `efuse`, `power_glitch`, `cpu_lockup`, `unknown`), `heap_free` and `heap_min` in bytes, `link` (`wifi`, `ethernet`, `none`), `link_up`, `broker_reconnects` (how many times the node has connected to the broker since it started; the first connection counts one).
* **Optional:** `board` (the build profile), `rssi_dbm` (-120 to 0, only on a Wi-Fi link that is up), `low_stack_tasks` (tasks with under 512 bytes of stack left at their worst), `last_error` (the last error line the node logged, at most 96 characters), and the memory told in two kinds: `heap_internal_free`, `heap_internal_min` and `heap_internal_largest` (the internal memory on its own: free now, the least it has been, the biggest block that could be allocated; the three go together) and `psram_free` (the external RAM, only on a board that has it). `heap_free` and `heap_min` count the external RAM too, so on a board with 8 MB of it they never look short; the internal figures are the ones that run out first.
* **The rules that join fields** (`validate_node_health`, which the vectors marked `"schema_valid": true` exercise): the least heap is never more than the heap free now, the internal memory is told whole with its least and its biggest block never above what is free, a signal strength goes only with a Wi-Fi link that is up, and no link means a link that is down.
* **What the server makes of it** (the node only tells): four warnings in the alarm centre - `node_low_memory` (under 30 KB of heap, cleared above 40 KB; or, when the node tells its internal memory, under 40 KB of it, cleared above 48 KB, or no free block of 8 KB; or a task short of stack), `node_frequent_resets` (three restarts in a day, or a crash in the last hour), `node_link_flapping` (three connections to the broker in a quarter of an hour, or the link down in two of the last six reports) and `node_weak_signal` (-80 dBm or worse in three reports in a row). A restart is seen when `uptime_s` goes back or `broker_reconnects` does. A node needs the broker's permission to write `armor/health/{node_id}` (`scripts/mqtt_identity.sh` of ARMOR-DEVOPS adds it).
* **Life state of the node (last will and birth, same topic):** each time a node connects to the broker it publishes `{"node_id": "<node>", "online": true}` on `armor/health/{node_id}` (retained), and its MQTT last will is `{"node_id": "<node>", "online": false}` on the same topic (retained, QoS 1). Nothing else is in either body, so neither can be taken for a report; a message that names another node than the topic is refused. The last message of the topic is therefore always the state of the node, also for a server that starts later. The radar node says the same on its presence topic `armor/node/{node_id}/health`. The broker rule that lets a node write its own `armor/health/{node_id}` already covers both.
* **How the last run ended, the gate, the core dump, the settings checks (all optional):** `boot` (`cause` - `panic`, `task_watchdog`, `interrupt_watchdog`, `other_watchdog`, `brownout`, `power_glitch`, `cpu_lockup`, `out_of_memory`, `guard_missing_task`, `guard_low_memory`, `guard_dead_man` or `guard` -, `reset_reason`, `uptime_before_s`, `heap_internal_free` and `heap_internal_largest` at the guard's last look, `coredump`, `deliberate`, `guard`), said only after a dirty start and only for the first ten minutes of the run; `memory_gate` (`closed`, `transitions` and the four levels it works by); `coredump` (`present`, `size`); `config_check` (`snapshot` `restored`/`failed`, `reverted` `reapplied`/`failed`). A node that crashed or restarted by its own guard says so once; the server keeps it in the node's log of restarts and in the History (`dirty_boot`).
* **Radar nodes only: the sensors.** `sensors` (up to three: `sensor_id`, `model`, `state`, `firmware_known` and `firmware`, `bluetooth` - `open`, `closed`, `none` or `unknown` -, `mac` only while the Bluetooth is open, `bluetooth_alert`, `quirk`) and `radar` (`perimeter_enabled`, `masked`, `wifi_jam`, `bridge_open`, `events_buffered`, `sensor_bluetooth_off`) come together and only from a node of the family `radar`. The only text taken from a sensor is its firmware and its address, both letters, digits and a few signs.
* **Compatible with older nodes:** nothing about the other messages changed. A node that does not send a report is simply listed as waiting for one.

## Arming profiles

An arming profile (`arm_profile.schema.json`) is a named way of arming an alarm panel: Away, Home, Night or one the owner made. The server keeps the list (`GET`/`PUT /api/v1/alarm/profiles`) and puts the chosen one **inside the arm command** (`alarm_command.schema.json`, property `profile`), so a node stores nothing in advance and an arm without a profile is exactly the command it always was.

* **A profile has:** `id` (up to 16 characters), `name` (1 to 32), `base` (`away` or `stay`: the mode the panel reports, and the default of the zones that say nothing - away guards every zone, stay leaves the interior ones out), and optionally `exit_delay_s` and `entry_delay_s` (0 to 300; absent means the node's own setting), `siren` (`false` is a silent alarm: still latched, recorded and told; absent means true), `notify` (`urgent` or `normal`: how loudly the **server** tells people, a critical alarm that is escalated or a high one; only the server reads it) and up to sixteen `zones`, each with the `id` of a zone and optionally `armed` (whether it guards in this profile) and `delay` (`instant`: it alarms at once; `entry`: it starts the entry delay first). A zone the node does not have is ignored.
* **What a profile never does:** it never switches off smoke, a panic button (an `always` zone) or a tamper, and never makes them quiet; it never touches the PIN, the lockout, the silence of a siren, the refusal of an arming over a sounding always zone or over a zone in trouble, or what a forced arming leaves out.
* **The rules that join fields** (`validate_arm_profile`, `validate_alarm_command`): a zone is named once, a zone that is left out (`armed: false`) has no `delay`, a profile goes only on an arm, and its `base` is the `mode` of the command.
* **The state** (`alarm.schema.json`) has two optional fields: `arm_profiles: true` (the node understands profiles; the server sends a profile only to a node that says so, because an older firmware answers nothing to a command it does not know) and `profile` (the id of the profile the panel is armed with; absent when it was armed without one or is not armed).
* **The server:** at most eight profiles, away and stay always present with their own base, the list replaced as a whole with a revision (a conflict is a 409, never a silent overwrite). The three it starts with are away, home (id `stay`) and night.

## Solar messages

`armor/solar/{node_id}/{device}/state` (node → server), `device` being lowercase letters, digits, `-` and `_` (at most 32 characters, not starting with `-` or `_`). The
payload repeats `node_id` and `device`; a mismatch is refused. The payload's `kind` picks the schema:

| Kind | Schema |
|---|---|
| `inverter` | `solar_inverter.schema.json`: the mode, the grid and output figures, the battery side (voltage, signed current, percentage), the panels' voltage, current and power, the temperature, three flags and the names of the active warnings (`warnings_known: false` says that the inverter's dialect cannot ask for them, so an empty list means unknown and not none) |
| `battery` | `solar_battery.schema.json`: how many modules are present (0 to 16) and, when there are, the state, voltage, current, temperature range, cell range, mean state of charge and alarm, and one entry per module (with, when the node reads them, the voltage of each cell and the module's temperature sensors, its model and the versions of its board and software, the number of cells, the current it allows each way, the speed of its console, the life counters, the health of each cell and the newest entry of its own event log, shown as the console prints it). With no module present the message carries no other reading |

An inverter message may also carry a second PV input (`pv2_v`, `pv2_a`, `pv2_w`; `pv_w` is then the sum of both) and, for a parallel system, `units` (up to ten entries) with the totals `total_out_w`, `total_out_va`, `total_load_percent` and `total_charging_a`; all of these are optional.

Both use `additionalProperties: false` and have no nulls: a reading a node does not know is left out.

## Electrical messages

`armor/electrical/{node_id}/state` (node → server; a channel may carry `power_estimated: true` when its power and energy are an estimate and not a measurement; a meter channel may also carry `reading_age_ms` and `errors`, how old its reading is and how many requests to it failed since boot, so a consumer tells a real 0 W from no data), one message per node every few seconds, `kind` `electrical` (`electrical.schema.json`). It carries `node_id`, `timestamp_ms`, `switching_enabled` (whether the node's firmware may switch anything at all; false unless it was built and set up for it) and up to sixteen `channels`. A channel has an `id` (lowercase letters, digits, `-` and `_`, unique in the message), `domain` (`ac` or `dc`), optionally a `label`, and `voltage_v`, `current_a`, `power_w` (positive when it draws from the network, negative when it feeds it), `energy_kwh`, and for AC `frequency_hz` and `power_factor`; `state` (`closed`, `open`, `unknown`) is what a switch's auxiliary contact shows, never what was asked; `alarm` is the meter's own flag. The message carries states and never a command. `additionalProperties: false` and no nulls, as for the others. See ARMOR-ELECTRICAL's `docs/ELECTRICAL_MESSAGES.md`.

## Alarm messages (contract version 0)

An ARMOR-ALARM node has one topic per leaf: `armor/alarm/{node_id}/state` (node → server, `alarm.schema.json`; a zone's state is `normal`, `triggered`, `tamper` or `trouble`, the last meaning that the node cannot read it), `armor/alarm/{node_id}/command` (server → node, `alarm_command.schema.json`) and `armor/alarm/{node_id}/result` (node → server, `alarm_result.schema.json`); none of them is retained. See ARMOR-ALARM's `docs/ALARM_MESSAGES.md`.

* **The state:** `phase` (`disarmed`, `exit_delay`, `armed`, `entry_delay`, `alarm`), `mode` (`disarmed`, `away`, `stay`), `siren`, `locked_out`, `commands_enabled`, up to sixteen `zones` (`id`, optionally `name`, `kind` `instant`, `entry`, `interior` or `always`, `state` `normal`, `triggered` or `tamper`, `bypassed`), `open_zones` (the ids that would stop an arming now) and the last ten `events` (`ago_s`, `kind` - among them `siren_silenced`, optionally the `zone`), oldest first. The message carries a state and never a command.
* **The command:** `command_id` (chosen by the server: sixteen lowercase hexadecimal digits), `action` (`arm`, `disarm` or `silence`; a silence stops the siren while the system stays armed and the alarm stays latched) and, on an arm only, `mode` (`away` or `stay`, required) and optionally `force` and a `profile` (see *Arming profiles* below; its `base` is the mode). There is **no PIN** (neither on a disarm nor on a silence): the PIN is for whoever stands at the panel, and the authority of the server is the broker's access list plus the node's own setting, so a command is refused by default at three independent places (the node's `server.commands`, the server's own switch and `scripts/mqtt_identity.sh alarm-commands`).
* **The answer:** the `command_id`, `action`, `accepted`, `refusal` (`none` exactly when accepted; otherwise `not_disarmed`, `zones_open`, `not_armed`, `bad_pin` or `locked_out`) and the `phase` the panel is in. **An accepted arm is not an armed alarm:** only the state message says that.

The rules that join two fields are in `validate_alarm_message`, `validate_alarm_command` and `validate_alarm_result` (a zone named once, an open zone that is a zone of the message, the mode `disarmed` in the disarmed phase and never in an arming or armed one (the alarm phase may carry both: a 24-hour zone or a tamper sounds with nobody having armed), a siren only in the alarm phase, an event about a zone of the message, a mode exactly on an arm, `force` only on an arm, the refusal that matches `accepted`); the conformance vectors that only those rules refuse are marked `"schema_valid": true`.

## Network messages

`armor/network/{node_id}/state` (node → server, `network.schema.json`), the state of the local network as one ARMOR-NETWORK node sees it, one message per node every ten seconds or when something happened; `kind` `network`; `timestamp_ms` and every `*_ms` are milliseconds since 1970 (the node is a program with a real clock). It carries the `interface` the node watches (`name`, `ip`, `cidr` always a private range, optionally `gateway`, `rx_bps`, `tx_bps`), the `internet` (`state`: `up`, `degraded`, `down` when the router answers and nothing beyond it does, `lan_down` when the router does not answer either, `unknown`; and optionally `since_ms`, `gateway_ok`, `latency_ms`, `loss_percent`, up to eight `probes`, the `last_outage`, `outages_24h` and `downtime_24h_s`), up to 512 `devices` and the latest 64 `events`, and optionally the `scan`. A device has an `id` (its MAC in lowercase with colons or, until the MAC is known, `ip-<address with dashes>`), an `ip`, `online`, `first_seen_ms` and `last_seen_ms`, and optionally `mac`, `randomized_mac`, `vendor`, `hostname`, `kind`, `os` (a guess), `latency_ms`, up to 64 `ports` (`port`, `proto`, `service`, `banner`) and up to 16 announced `services`. An event has an `id` that never repeats (a reader that sees it twice counts it once), a `kind` (`new_device`, `device_online`, `device_offline`, `ip_changed`, `arp_conflict`, `port_opened`, `port_closed`, `internet_down`, `internet_up`, `gateway_down`, `gateway_up`) and a time; the device kinds name a `device_id` (and a `port` when they are about one), the internet and gateway kinds name neither, and only the two `_up` kinds say how long it was down (`outage_s`). `validate_network_message` checks those rules that join two fields (a device and an event named once, a MAC that is the id, a first sighting that is not after the last, what an event names), which the schema cannot state. The message carries findings, never a command. See ARMOR-NETWORK's `docs/MESSAGES.md`.

Two optional parts were added to the network message. `public` is what the internet sees of the connection, asked of a public service now and then (a node can opt out): the public `ip`, optionally `hostname`, `city`, `region`, `country`, `org` (the provider and its autonomous system), `timezone`, `checked_ms` always, and `changed_ms` when the address was seen to change. `results` (at most 16, oldest first) is what the node did with the manual orders the server handed it in the answer to its previous message (a sweep now, a ping, a traceroute, a wake-up, a look at the ports of one device, a look at its web page): each has the `id` of its order, a `type` (`scan_now`, `ping`, `traceroute`, `wake`, `ports`, `http`, `inspect`), `ok`, `finished_ms` and optionally `device_id`, `output` (at most 2000 characters), `ports` and `latency_ms`; the server counts a result it reads twice once. An `inspect` order may carry `auth` (`user`, `password`), the login kept on the server for that device, and the node never prints it back; the server keeps those logins encrypted (`PUT/DELETE /api/v1/network/devices/{id}/login`, administrators only) and shows only whether one exists and its user.

The orders travel the other way inside the **answer** the server gives to `POST /api/v1/network/state` (and are never sent over MQTT): `{ "commands": [{ "id", "type", "device_id"?, "ip"?, "mac"?, "port"? }] }`, at most four at a time, each handed out once. A node refuses any order whose address is not on the network it watches.

## Switches: the state, the command and the answer

A node that controls a **switch** (a source transfer: two contactors, A and B, onto one line, never both) says so in the ordinary state message and takes commands on its own topic. Every command is refused by default at three independent places: the node (its firmware has to be built and set up to switch, `switching_enabled`), the server (`ARMOR_ELECTRICAL_SWITCHING=1`) and the broker (its ACL has to allow the topic, `scripts/mqtt_identity.sh electrical-switching`). Nothing that switches has been built.

* **The state** (`electrical.schema.json`, an optional `switches` array of at most four, every `id` once): for each switch `id`, `kind` (`transfer`), optionally `label`, `source_a` and `source_b` (the ids of the channels that measure each source), `a_closed` and `b_closed` (the auxiliary contacts: what the node **sees**, never what was asked), `selected` (`none`, `a` or `b`: the source confirmed closed onto the line), `wanted` (where the controller is going), `closing` (a coil is energised and the contact has not confirmed), `armed` (the next request to close is accepted) and `fault` (`none`, `did_not_close`, `did_not_open`, `both_closed`, `disabled`; a latched fault opens everything until it is acknowledged with both contactors confirmed open).
* **The command** `armor/electrical/{node_id}/command` (server → node, `electrical_command.schema.json`, never retained, at most once): `node_id`, `timestamp_ms`, `command_id` (chosen by the server, 8 to 32 lowercase letters and digits), `switch` and one `action` from the allow-list `arm`, `close_a`, `close_b`, `open`, `acknowledge`. **Closing is two steps:** `arm` (the node answers with a one-time `token`), then `close_a` or `close_b` carrying that `token`; a token is present exactly on those two actions. The token is spent by the first close that presents it, and a wrong one also withdraws the arm, so an old message that turns up again finds nothing to match and moves nothing. `open` needs no token and is always accepted.
* **The answer** `armor/electrical/{node_id}/result` (node → server, `electrical_result.schema.json`, never retained): the `command_id` it answers, `switch`, `action`, `accepted` and `refusal` (`none` exactly when accepted; otherwise `disabled`, `fault`, `not_armed`, `not_confirmed_open`, `unknown_switch`, `bad_token` or `not_supported`); the answer to an accepted `arm` carries the `token`. **An accepted command is not a switch that closed:** only the state message says that.

The schema cannot say the rules that join two fields (a token on the closing actions only, the refusal that matches `accepted`, a switch named once); `validate_electrical_command`, `validate_electrical_result` and `validate_electrical_message` do, and the conformance vectors that only those rules refuse are marked `"schema_valid": true`. See ARMOR-ELECTRICAL's `docs/SWITCHING.md` and `docs/SAFETY.md`.

## Writing to a Pylontech battery: the order and the answer

A gateway node (ARMOR-SOLAR) can change what a Pylontech battery keeps, through the battery's console, as the maker's own tool does. It is **off by default at three independent places**: the node (its setting `battery.write_enabled`, with the battery's service password stored only there), the server (`ARMOR_BATTERY_WRITE=1`) and the broker (its access list has to allow the two topics below). Only **typed operations** exist: there is no free command (the expert console is a typed operation with a block list). The operations, their risk, the values they take and the ranges are one table, `src/armor_common/battery_ops.json` (the ranges are the ones the maker's tool states; where its files state an order between two values, that order is checked and a group of values is only accepted whole).

* **The order** `armor/solar/{node_id}/maintenance/command` (server → node, `solar_battery_command.schema.json`, never retained, at most once): `node_id`, `timestamp_ms`, `command_id` (8 to 32 lowercase letters and digits), `port` (1 to 10) and one `action`. **Writing is two steps:** `arm` (carries `op`, `params` and the `serial` number the person typed; the node logs in, reads the battery, checks every precondition and answers with a one-time `token` and the exact operation it would do) then `execute` (the same `op`, `params` and `serial`, plus the `token`, within two minutes). `cancel` stops an operation that may still be stopped; `stage` carries one piece (256 bytes in base64) of a firmware image to the node before a `firmware_update` is armed. The schema allows each `params` name with its type; the ranges and the order between values are in `validate_solar_battery_command`, which uses the table.
* **The answer** `armor/solar/{node_id}/maintenance/result` (node → server, `solar_battery_result.schema.json`, never retained): the `command_id`, `port` and `action` it answers, a `stage` (`armed`, `started`, `progress`, `cancel_requested`, `final`, `rejected`, `staged`), `accepted` and `refusal` (`none` exactly when accepted; the other words are the refusals of the table). An `armed` answer carries the `token`, the `canonical` operation, a `summary`, its `risk`, whether it is `atomic` (never cancelled once it begins to write), the identity of the battery and what was read before. A `final` answer carries the `outcome` (`ok`; `failed`, also when the read-back differs from what was written; `partial`, a sequence that stopped midway; `retry`, nothing was written and asking again is safe), a short `code`, the reads `before` and `after` the writes and the redacted `transcript`. **An accepted order is not an operation that worked:** only a `final` answer with `ok`, and the read-back it carries, say that. The service password of the battery has no field anywhere and every text that is kept has it replaced.
* **The rules that join fields** (`validate_solar_battery_command`, `validate_solar_battery_result`; the vectors only they refuse are marked `"schema_valid": true`): what each action carries (an `arm` an `op` and a `serial` and no token; an `execute` also a token; a `cancel` nothing more; a `stage` only the piece), the values of the operation against the table, the refusal that matches `accepted`, a token only in an `armed` answer, and the fields each stage must have.
* **What the node refuses before it writes:** a battery that is not there, of a model or firmware it does not know, whose serial number differs from the one typed, that is not idle (the operations that need it), that has a critical alarm (except the recoveries: restart, shutdown, clearing a fuse fault, switching an output off), one operation at a time per port, a pause after a write, and three wrong tokens in ten minutes lock every order for five. A firmware image is sent only when the battery's model, its chip (read from its Board and from characters 8 and 9 of its serial number, which must agree) and the image's own header (board name at offset 0x418, version at 0x400) fit together.

## Controlling a node: restart, pause, standby, identify, diagnostics and maintenance

The server can give a node one typed order without opening the node's configurator. It is the same two steps as a switch or a battery write: the server **arms**, the node answers with a one-time **token bound to the operation**, the server **executes** with that token. The token lives 30 seconds, is used once, and a node holds one at a time; an execute for another operation than the one armed is refused as `invalid_token` and spends the token.

* **The order** `armor/control/{node_id}/command` (server → node, `node_control_command.schema.json`, never retained), or `armor/control/all/command` (server → every node, an `arm` only). Fields: `node_id`, `timestamp_ms`, `command_id`, `action` (`arm`, `execute`), `operation` (`restart`, `pause`, `resume`, `standby`, `identify`, `diagnostics`, `maintenance_on`, `maintenance_off`), `mode` (`now`, `rolling`), `requested_by` and, where they belong, `delay_s`, `slot`, `duration_s` and `token`. Only the server identity may publish there (the broker's ACL); a node subscribes to its own topic and to `all`.
* **The answer** `armor/control/{node_id}/result` (node → server, `node_control_result.schema.json`, never retained; never `all`): the `command_id`, `action` and `operation` it answers, a `stage` (`armed` with the token and its life; `restarting`, the acknowledgement sent before the reboot, with the reason, the mode, the seconds until it goes, the uptime, the firmware and for whom; `applied` with the new `state`, the `maintenance` flag, the seconds left, since when and for whom; `diagnostics` with the read-only snapshot; `rejected`), `accepted` and a typed `refusal` (`none`, `not_armed`, `invalid_token`, `token_expired`, `rate_limited`, `already_restarting`, `already_in_state`, `busy_update`, `busy_upload`, `busy_slot_copy`, `busy_battery`, `unavailable`).
* **What the operations do:** `restart` is the clean restart (the node closes its connections first; its settings are kept; `rolling` waits `slot` times thirty seconds so that nodes never restart together; at most one per 60 seconds). `pause` stops the node's work for 60 to 3600 seconds (3600 when absent) and resumes by itself; a restart also ends it. `standby` switches the node's work off with no end and across restarts, but the node stays connected, keeps answering and keeps its outputs in their safe state: it is not a power-off. `resume` ends a pause or a standby. `identify` blinks the node's LED or shows a banner for 5 to 300 seconds (30 when absent), never a siren. `diagnostics` is a snapshot. `maintenance_on` and `maintenance_off` set a flag the node reports and the server uses to hold back the node-offline alert for 60 to 28800 seconds (3600 when absent).
* **What no order can do:** there is no factory reset, no erase of settings or credentials and no deep sleep or wake timer: they are not words of the contract, and the vectors check that every attempt is refused.
* **The rules that join fields** (`validate_node_control_command`, `validate_node_control_result`; the vectors only they refuse are marked `"schema_valid": true`): a token exactly on an execute, never an execute for `all`; a delay and a slot only on the execute of a restart, a slot only in mode `rolling`, mode `rolling` only for a restart; a duration only on the execute of `pause`, `identify` or `maintenance_on` and inside that operation's range; in an answer, `refusal` is `none` exactly when it was accepted, the stage fits the action and the operation (an accepted arm is `armed`, a restart `restarting`, diagnostics `diagnostics`, the rest `applied`) and each field appears only in its own stage.
* **In the health report** (`node_health`): optional `control_state` (`running`, `paused`, `standby`), `control_since_ms`, `control_by`, `control_until_s`, `maintenance` and `maintenance_until_s`, so a console shows "Standby since ..., by ..." and "Paused"; the since, by and time-left fields go only with the state they describe.
* **In the history** (`system_event`): the words `control_requested`, `control_acknowledged`, `control_applied`, `control_refused`, `control_back` and `control_lost`; there is no free text.
* **The HTTP side** (`openapi/armor-server.yaml`): `POST /api/v1/nodes/{id}/control`, `POST /api/v1/nodes/control` and `GET /api/v1/nodes/control/operations` (and `/{id}`), for an administrator who proved themselves again a moment ago; restart, pause and standby also need the name of the node (or the word RESTART, PAUSE or STANDBY for all of them) typed.

## Diagnostics of a node: the package, the log and the read-only token

* **Asking for them.** The execute of a `diagnostics` order may carry `detail`: `package` or `log` (only there; an arm, another operation or another word is refused). The node answers inside `diagnostics.package` of its `node_control_result`: for `log`, `{detail, log, truncated}` and nothing else; for `package`, also the memory (`heap`), the tasks with the least stack each has had (`tasks`, at most 40), why it last started (`resets`, `boot`), the gate (`memory_gate`), the versions (`versions`, with the sensors' firmware), the settings it may show (`config`) and the summary of its core dump (`coredump`, with the task, the reason, the program counter and a backtrace of at most sixteen addresses). A node sends at most one every fifteen seconds (`rate_limited` otherwise).
* **What can never be in it.** The package is built on the node the other way round from "everything but the passwords": only the leaves of a fixed list of names go in, and as short text (so `config` is a map of text to text, 64 entries at most, 96 characters each); a name that says pass, secret, token, key, pin, user, cert, session and the like is never carried; the address of the broker is carried as scheme, host and port only; and every secret the node knows is washed out of the whole package, the log included. The schema allows no other member, and the server reads the package member by member, so a member a node adds on its own never reaches a console. The vectors include packages with a member for a password, a task state outside the list and an address that is not one.
* **The read-only diagnostic token** (HTTP, `openapi/armor-server.yaml`; `diagnostic_token_request`, `diagnostic_token_created` and `diagnostic_token_info`). An administrator who has just proved who they are asks `POST /api/v1/diagnostics/tokens` for a token for one to sixteen nodes, for 300 seconds to 24 hours (two hours when `ttl_s` is absent). The answer carries `token` (`armor-diag-` and 43 characters) **once**: the server keeps only its SHA-256, the list (`GET /api/v1/diagnostics/tokens`) never shows a secret or a hash, and a lost token is revoked (`DELETE /api/v1/diagnostics/tokens/{id}`) and replaced. The token reads, with GET and nothing else, `/api/v1/diagnostics/nodes`, `/nodes/{id}`, `/nodes/{id}/package` and `/nodes/{id}/log` for the nodes it names - what the server already holds, never a node - and it is no credential anywhere else. Every refusal of an unknown, expired or revoked token is the same 401. Issue, use and revocation are in the audit trail and the History (`diagnostic_token_issued`, `diagnostic_token_used`, `diagnostic_token_revoked`, `diagnostic_token_denied`).

## The events of a radar node's perimeter engine

`armor/radar/{node_id}/events` (node → server, `radar_event.schema.json`, validated by `validate_radar_event`, QoS 1, never retained): one short message when the node's own perimeter engine or one of its sensors finds something. `event` is one of `zone_occupied`, `zone_clear`, `loiter`, `tripwire`, `path_violation`, `masking`, `masking_end`, `sensor_bluetooth_open`, `sensor_bluetooth_closed`, `wifi_jam`, `wifi_jam_end`, `bridge_opened`, `bridge_closed`; the rest are optional and fixed in kind: `name` (a zone, a line or a sensor model, 24 characters), `sensor_id` (1 to 3), `track_id`, `movement` (`still`, `walking`, `running`), `value` and `count`, `direction` (`in`, `out`; a tripwire only), `from` (the zone it came from; a path violation only) and `by` (the administrator who opened the serial bridge; the bridge only). There is no free text, so nothing secret can be in it. `boot` (random at each start of the node) and `seq` (counting inside that start) name an event: a server that gets the same pair twice keeps one, which is how a node can safely send again, in order, the last thirty events it kept in its flash while the broker could not be reached. The broker's access list lets a node write only its own subtree.

## Planned maintenance: the node says it is going quiet

* **The signal** `armor/control/{node_id}/maintenance` (node → server, `node_maintenance.schema.json`, validated by `validate_node_maintenance`): the only **retained** message of the control family. Fields: `node_id`, `timestamp_ms`, `active`, `reason` (`restart`, `pause`, `standby`, `update`, `upload`, `operator`), `firmware`, optionally `expected_s` (1 to 3600: how long the node expects to be quiet; only while `active`) and `requested_by`. A node publishes `active: true` before it goes quiet on purpose (right with the `restarting` answer, before a pause or a standby, before a firmware install, a slot copy or a panel upload) and `active: false` when it is back; the clearing message is retained too, so the broker never keeps a stale `active`. A node that boots into standby keeps `standby` active until it is resumed. The broker's ACL lets a node publish only its own topic; the server reads `armor/control/+/maintenance`.
* **What the server does with it:** an active signal is the reason for an expected silence, so the node-offline alert and the tamper inference are held back for that node, but only up to the server's own bound (10 minutes unless set); after it the node counts as offline again and the history records `maintenance_expired`. A node that returns (a health report with a lower uptime, or `active: false`) closes the window. The history words are `maintenance_started`, `maintenance_ended` and `maintenance_expired`. A stuck or hostile node therefore cannot silence the alerts for ever.

## Keeping every implementation in step

1. **Python** (`armor_common`) interprets the schema files directly with a small
   validator that *refuses* a schema using a keyword it does not implement, so a
   constraint can never be quietly skipped.
2. **Conformance vectors** (`conformance/*.json`) list payloads that must
   be accepted and payloads that must be rejected. Every implementation runs them:
   `armor_common` in its own tests, ARMOR-SERVER in `tests/conformance.test.ts`. A
   disagreement fails a build; tightening a contract means adding a vector here.
3. **Generated types** (`generated/armor-contracts.ts`, `generated/ArmorContracts.kt`)
   come from the schemas with `python tools/generate_types.py`; `--check` fails when
   they are stale.

## HTTP

`openapi/armor-server.yaml` describes every route of ARMOR-SERVER, who may call
it (an explicit security list on every operation) and a named schema for every
request body, answer and error; the examples in the schemas are checked against
them. `tests/test_openapi.py` fails when the contract is not valid OpenAPI, when
a body is described as a bare object, and, with ARMOR-SERVER checked out next to
this repository, when the routes the server registers differ from the ones the
contract describes (method and path).

## Changing a contract

1. Edit the schema. 2. Add the accepted and rejected vectors. 3. Run
`python -m unittest discover -s tests` and `python tools/generate_types.py`.
4. Update every implementation until its conformance test passes. 5. Bump the
schema `$id` version when the change is not backwards compatible.

## Connection and system events of the history

`connection_event`, `system_event` and `connection_client` describe what the history of the server says about the clients that connect to it (a Studio session, the Android app, the panel of a node, the voice service) and about the system itself (a node that appears or disappears with its firmware, the broker link, a setting that changed, a service, an update, the alarm armed or silenced). They are published for the clients that read `GET /api/v1/history` and `GET /api/v1/history/connections`; they are not MQTT messages. Their words are a fixed list and none of them has a field where a secret could go; the address and the user agent are written for administrators only and the server takes them out of the answer to anybody else.

In the History a node that started after a crash or by its own guard is told once (`dirty_boot`, the cause in `profile`), a sensor whose own Bluetooth opens or closes is told with the node and the sensor in `subject` and its model in `profile` (`sensor_bluetooth_open`, `sensor_bluetooth_closed`), the events of the perimeter engine that matter by their word (`radar_event`), and the diagnostic tokens by their id (`diagnostic_token_issued`, `diagnostic_token_used`, `diagnostic_token_revoked`, `diagnostic_token_denied`, always in the category `settings`).
